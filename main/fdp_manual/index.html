FAIR data pipeline manual

Managing code runs

DataPipeline.initialise — Function
initialise(config_file = $FDP_CONFIG_DIR/config.yaml,
           submission_script = its run_metadata.script_path;
           token = $FDP_LOCAL_TOKEN)

Read the working config that fair run wrote, register the config, the submission script and the code repository with the local registry, open a new code run, dated in UTC, and return the DataRegistryHandle the rest of the API works on. The registry is run_metadata.local_data_registry_url (default http://127.0.0.1:8000/api/) and the API version run_metadata.api_version (default 1.0.0). token is the registry's access token, which registering needs; fair run sets FDP_LOCAL_TOKEN to it.

With no arguments, the files are those in the folder fair run names in FDP_CONFIG_DIR when it launches a script: a call with that unset, or with a file that is not a working config, throws a ConfigFileException saying so. The submission script is the one the working config names as run_metadata.script_path - the copy fair run wrote in that folder, script.sh, or script.jl for a user config with shell: julia, and so on - else script.sh (script.bat on Windows) in the folder. After rehearse the same call opens a Rehearsal instead, from the job folder it prepared: nothing is registered, and the handle holds no token, whatever is given or set.

A session has one run, opened once, however the files are given: a second call while the run is open, or after finalise or discard has ended it, is a ReadWriteException - for a rehearsal, to rehearse again; for a recorded run, since a script making several runs is not supported.

The code repository is registered at its commit as one object, kept where the registry holds one already. A new one has the repository's own authors, read from the first of its metadata files that it has - codemeta.json, .zenodo.json, CITATION.cff, JuliaProject.toml, Project.toml - as it is at the commit in the clone run_metadata.local_repo, or in its working tree for a run from uncommitted changes; where that file lists none, the runner. The licence and keywords that file gives are added to the object either way. Nothing is taken from the files after it, even what it lacks, and what they say more or otherwise is told; that file being unreadable is an error.

A code repository with uncommitted changes, which fair run --dirty records as a <commit>-dirty commit, gets a warning and an issue saying that the code that ran cannot be recovered from its commit.

DataPipeline.finalise — Function
finalise(handle)

Complete the code run: name every output file by its hash and register it, register the issues raised, attach the inputs and outputs to the code run, and append the code run's uuid to coderuns.txt beside the working config, where the CLI's fair add and fair push find it. Return the data store's root, the folder under which the output files now sit, by namespace and data product. In a Rehearsal nothing is registered and the outputs are collected in its folder instead, which is returned.

A file whose bytes are those of the highest version of its data product already registered is not registered again: no version is made, the file written is removed, and it is not an output of the code run. Where a link call named its source, the source, authors and licence registered with that version must be the same as well. A file written as a version that is registered already must be that version's in the same way - a reproduction, likewise not registered again - or nothing is registered, and the call is an error naming the version.

source
finalise(handle::DataRegistryHandle{Rehearsal})

End a rehearsal, registering nothing. The outputs are checked as a recorded run checks them: that each source is one file, that each written as a version registered already reproduces it, and whether each file is the one registered as the highest version of its data product, which is reported. They are then moved to the outputs folder as <namespace>/<data product>/<version>.<extension>, replacing what is there, with the working config and the script copied beside them. The issues raised are printed, the data store's empty directories pruned, the job folder deleted if rehearse had fair prepare it, and the session's rehearsal ended. Return the outputs folder. A handle whose rehearsal has ended cannot be finalised again.

DataPipeline.DataRegistryHandle — Type
DataRegistryHandle{M <: AbstractRunMode}

The state of one code run, created by initialise and completed by finalise. Every other function in the API takes one. M is the run's AbstractRunMode, which decides what the run registers.

Fields

  • mode: the run's mode, an M
  • config: the working config, as read from config.yaml
  • config_dir: the directory the working config was read from, where coderuns.txt is appended to at finalise
  • registry: the RegistryEndpoint every request goes to
  • config_obj: registry URL of the object for the working config file, or nothing in a run that registers none
  • script_obj: registry URL of the object for the submission script, or nothing
  • repo_obj: registry URL of the object for the remote code repository, or nothing
  • datastore_obj_url: registry URL of the storage root for the data store, or nothing
  • code_run_obj: registry URL of the code run, or nothing
  • code_run_uuid: the code run's uuid, as the CLI's staging refers to it
  • inputs, outputs: metadata of what has been read and written so far, keyed by (data_product, component), with component nothing for a whole file
  • unchanged: what was written and found to be registered already, so that no version was made of it and it is no output of the code run; keyed as outputs is
  • issues: issues raised so far, registered at finalise
  • citations: the citations read by register_citations!, by key
  • doi_lookups: the citations looked up from a DOI so far, by the DOI's URL
  • authors: the identifiers that register_authors! has been given for each author's name

DataPipeline.AbstractRunMode — Type
AbstractRunMode

The way a code run is being made, which decides what the API registers. A DataRegistryHandle carries its run's mode as its type parameter. A RecordedRun registers everything; a Rehearsal nothing.

source
DataPipeline.RecordedRun — Type
RecordedRun()

The mode of a code run made under fair run: its working config, script, repository and code run are registered at initialise, and its outputs, issues, inputs and outputs at finalise.

source
DataPipeline.Rehearsal — Type
Rehearsal(outputs)

The mode of a run that registers nothing, prepared by rehearse: the script runs as fair run would run it, reading what the registry holds and writing to the data store, and finalise collects what it wrote in the folder outputs, as <namespace>/<data product>/<version>.<extension>, beside the working config it ran under. The handle holds no registry token.

source
DataPipeline.RegistryEndpoint — Type
RegistryEndpoint(url, api_version = "1.0.0"; token = nothing)

A data registry to talk to: the base url of its REST API (with a trailing slash, e.g. "http://127.0.0.1:8000/api/"), the api_version sent in the Accept header of every request, and the access token sent with them, if there is one. Reading needs no token; registering anything does. initialise builds one from run_metadata.local_data_registry_url and run_metadata.api_version in the working config, with the token that fair run puts in FDP_LOCAL_TOKEN.

The token is never shown when the endpoint is printed.

source
DataPipeline.ReadWriteException — Type
ReadWriteException(msg)

Thrown when the registry or the data store does not hold what a read or write needs: a missing data product, a version already registered, a registry that is not running, a write with no registry token; or when a read or write asks for what is not yet implemented, such as a table.

source
DataPipeline.ConfigFileException — Type
ConfigFileException(msg)

Thrown when a configuration file - the working config, or the CLI's own - lacks the section or entry a call refers to.

Rehearsing a run

A script can be run through the pipeline without being recorded, to be run again, unchanged, under fair run once it is right. In a session, prepare the run from the user config, then run the script, or its lines one at a time:

using DataPipeline
fair"pull config.yaml"                 # when inputs need registering or syncing
DataPipeline.rehearse("config.yaml")   # fair prepares the job as a run would
include("script.jl")                    # or its lines, one at a time

rehearse has fair write the working config and the script into a job folder, as fair run does before it launches a script, and the session then holds the rehearsal: that folder, the folder the outputs will be collected in, and the handle once opened. The script's initialise() opens a rehearsal rather than a code run: it reads what the registry holds, writes to the data store, holds no registry token, and registers nothing, saying instead what link_register! and register_authors! would have registered. Its finalise checks the outputs as a recorded run would, saying which are registered already, unchanged, moves them to the outputs folder as <namespace>/<data product>/<version>.<extension> with the working config beside them, prints the issues a recorded run would have raised, deletes the job folder fair prepared for it, and returns the folder. discard ends a rehearsal without collecting anything.

A session has one run, opened once: initialise() is an error while a run is open, and after finalise or discard has ended it. In a rehearsal the error says to rehearse again, which prepares a fresh one; a script that failed halfway is run again that way, with restart = true while the first rehearsal is still open. A recorded run cannot be followed by another in the same session. The outputs folder is a new one under the system's temporary directory, unless outputs = names one, in which case a repeated rehearsal replaces its files. local_only = true passes --local to fair run. Nothing of a rehearsal reaches the registry, so a model run can be rehearsed only once the fetch run it reads from has been recorded.

A script can also rehearse the run it belongs to, as a check before that run starts. In a script that fair run launched, DataPipeline.rehearse() do handle ... end rehearses the job fair run prepared, passes the block the rehearsal's handle, and discards the rehearsal as the block ends, so that the script's initialise() then opens the recorded run as usual. A fetch run that finds nothing left to fetch can stop there, before a code run is registered:

using DataPipeline
nothing_to_fetch = DataPipeline.rehearse() do handle
    return all_fetched(handle)    # the script's own check
end
nothing_to_fetch && exit()
handle = DataPipeline.initialise()

Under fair run a script rehearses in a block only: rehearse given a path is refused there, since the script's initialise() would open that rehearsal in place of the run, and record nothing. Elsewhere a block takes a path, as rehearse does.

The fair used is the one DataPipeline.set_cli!(path) has recorded, a preference of the environment DataPipeline is loaded from that holds across sessions; else the fair on the path, which it is on when Julia was started from a shell with the CLI's virtual environment active; else the copy the package installed. fair"..." runs it with any arguments, written as on the command line: fair"pull config.yaml", or fair"pull $config".

A Julia started by an editor has no virtual environment on its path, so the package can install a copy of its own, with a Python and a git of its own that MicroMamba fetches: DataPipeline.install_cli!(), once, which records the copy as the fair to use, and again to bring it up to date. The whole pipeline can then be set up from Julia:

using DataPipeline
DataPipeline.install_cli!()            # once: fair, with its Python, recorded
fair"registry install"                 # once: the local registry
fair"init"                             # once per project, from its root; asks questions
fair"pull config.yaml"
DataPipeline.rehearse("config.yaml")
DataPipeline.rehearse — Function
rehearse(path; outputs = nothing, local_only = false, restart = false)
rehearse(f, [path]; outputs = nothing, local_only = false, restart = false)

Prepare this session to run a script through the pipeline without recording it. The script then runs unchanged: its initialise opens a Rehearsal rather than a recorded code run, its reads and writes go as they would, and its finalise collects the outputs in a folder and registers nothing. path is a user config, which is prepared as fair run prepares one, from the project the config is in and with --local if local_only is true: by fair run --rehearse, which writes the working config and the script into a new job folder, registers and stages nothing, and makes no git check, and which fair-cli has from 0.11.0. Or path is that job folder itself, or the working config in it. Return the job folder.

outputs is the folder the outputs are collected in, made if need be; by default a new folder under the system's temporary directory, which lasts as long as the system keeps it. The session keeps the rehearsal - the job folder, the outputs folder, and the handle once opened - and initialise() opens it once: a second call is an error until finalise or discard has ended it, and after that too, until rehearse is called again. A second rehearse before the rehearsal has ended is an error unless restart is true, when the rehearsal in progress is discarded first: its handle's files removed from the data store, and its job folder deleted if rehearse had fair prepare it. A job folder given as path is not deleted. A session that has recorded a code run cannot rehearse. A token in the environment is not used by a rehearsal.

With a function f first, as a do block, the rehearsal is a check: its handle is opened at once and passed to f, the rehearsal is discarded when f returns or throws - what f wrote removed from the data store - and f's value is returned. The session is then empty, so that a script's initialise() opens the run it was launched for. With no path, the rehearsal is of that run, the job folder fair run names in FDP_CONFIG_DIR, so that a script can find out whether it has anything to do before a code run exists:

nothing_to_do = DataPipeline.rehearse() do handle
    return isempty(missing_inputs(handle))    # the script's own check
end
nothing_to_do && exit()
handle = DataPipeline.initialise()

A block prints one line, the run after it saying again what a rehearsal says as it opens, and an outputs folder made for it is removed if f left nothing there. A script that fair run launched, which sets FDP_SESSION for it, rehearses in a block only: rehearse(path) there is an error, since its initialise() would open the rehearsal in place of the run fair run prepared, and record nothing.

The rehearsal's script reads the local registry, so the rehearsal keeps it running until finalise or discard ends it: through a session of the CLI's, which ends with it - and, run by fair run, through the run's own session. A registry that fair registry start started runs until fair registry stop either way.

The fair that prepares a user config is the one set_cli! recorded, else the fair on the path, else the copy install_cli made, and with none of those the call fails saying so. Julia started from an editor has no virtual environment on its path, which is what the last two are for. @fair_str runs the same fair with any arguments.

DataPipeline.discard — Function
discard(handle)

End a rehearsal without collecting its outputs: remove the files it wrote to the data store, delete the job folder it ran from if rehearse had fair prepare it, and end the session's rehearsal. Return nothing. A handle whose rehearsal has ended only has its files removed. A recorded code run, being registered already at initialise, cannot be discarded: it ends with finalise.

DataPipeline.@fair_str — Macro
fair"arguments"

Run the pipeline's command-line tool fair with its arguments written as on the command line, in the current directory, printing what it prints: fair"pull config.yaml" is fair pull config.yaml. The text is split as Julia's backticks split a command, so quotes group a word, and $name and $(expression) interpolate, as in fair"pull $config". An exit status other than 0 is a ReadWriteException. The fair run is found as rehearse finds it: the one set_cli! recorded, else the one on the path, else the copy install_cli made. A command that asks questions, as fair init does without --ci, needs a terminal.

DataPipeline.set_cli! — Function
set_cli!(path)
set_cli!(nothing)

Record path as the fair this package runs - by rehearse and @fair_str, before any fair on the path or the copy install_cli made - after checking that it runs. The record is a preference in the LocalPreferences.toml of the first environment on the load path that has DataPipeline: the active one where DataPipeline is among its dependencies, else the one it is loaded from, such as the default environment. DataPipeline.install_cli — Function
install_cli(; version = nothing, python = nothing)

Install the package's own copy of fair, or bring it up to date, and return the path of its executable. The copy lives in a scratch space of the package's, with a Python and a git of its own that MicroMamba fetches from conda-forge, so it needs no Python, no git and no virtual environment on the machine, and rehearse and @fair_str use it when no fair is on the path, running it with its own programs on the path. fair-cli is installed from PyPI at its newest version, or at version; run again, the call brings the copy up to date, printing its version before and after. The Python is 3.12 unless python names another minor version; a change rebuilds the environment, as does an environment whose Python no longer runs. A registry installed through this copy has an environment of its own built with the copy's interpreter, so after such a rebuild it must be installed again: fair registry stop, then fair registry install --force, which a CLI may refuse while the registry runs. Needs the network.

DataPipeline.link_read! — Function
link_read!(handle, data_product; path = nothing, force = false)
link_read!(handle, pattern)

Return the path of the file behind a read: data product of the working config, recording it as an input of the code run. A data product with no file, such as a deposit, which a register: entry with no_file: true or link_register! with no path registers, is recorded as an input in the same way, and nothing is returned.

The file is in the data store, named by its hash. For code that needs its input under a name or in a place of its own, path asks for the file there, and is what is then returned:

  • with nothing at path, the file is put there, any missing directories being made: as a hard link to the data store's file where one can be made, so that no bytes are copied, else as a copy;
  • a file already there with the same contents is left exactly as it is, whether it is the data store's file under a second name or a copy of it;
  • a file there with other contents is an error, and nothing is overwritten, unless force is true, when it is replaced by the registered file. A directory there is always an error.

A file that is a hard link is the data store's own, so it must not be written to. force does nothing without path. A data product with no file takes no path.

Given a pattern instead - a name with one or more *, each matching one segment of a name, so that era5/t2m/* matches era5/t2m/1940-1949 but not era5/t2m/a/b - return the path of a temporary directory holding the file of every read: data product that matches, each recorded as an input (the directory itself is not), a data product with no file being recorded and given none. Each is a symbolic link to the data store's file where one can be made, else a hard link, else a copy, as on a Windows machine that allows no symbolic links. Where the working config keeps the pattern's own entry, as a CLI may, a pattern that matches nothing gives an empty directory; where it does not, that is an error. Each is named after its data product with / replaced by _, plus the file's extension; the directory is named by the SHA-1 of the sorted list of those names and the files' hashes, so the same set of files gives the same name. The directory is removed when Julia exits. A pattern takes no path.

See also: canread

DataPipeline.link_write! — Function
link_write!(handle, data_product; path = nothing, supersede = false,
            doi = nothing, bibtex = nothing, title = nothing,
            primary = nothing, description = nothing,
            original_store = nothing, licence = nothing, license = nothing,
            release_date = nothing, release_version = nothing)

Return a path to write a write: data product of the working config to, in the data store, recording it as an output. finalise names the file by its hash and registers it, replacing ${{RUN_ID}} in the registered name with the code run's uuid.

path names a file that exists already, to be registered as the data product in place of one the caller writes. It is put in the data store - as a hard link where one can be made, so that no bytes are copied, else as a copy - and its path there is returned; the file at path is left as it was. Its extension must be the entry's file type. A hard link is the same file under a second name, so the file must not be written to afterwards.

A file whose bytes are those of the highest version of the data product already registered is not registered again: no version is made and it is not an output of the code run. Where the call names a source, the source, authors and licence registered with that version must be the same as well. The version the write: entry names may be one registered already, when the file must be that version's in the same way - a reproduction, likewise not registered again - or it is an error. With a path this is found as the call is made, and the path returned is that of the registered file; a file that is written afterwards is found so by finalise, before it registers anything.

A file that comes from somewhere else is registered with its source. The source is named by its doi, or by bibtex, the key of a citation that register_citations! has read - one or the other. A DOI with no citation registered for it is looked up: its formal metadata, DataCite's record of it or else its CSL record, gives what it has of the title, the description, the licence, the release date and version, and the authors with their ORCIDs or ROR ids. Each keyword below takes the place of what the citation says, and the title and the release date must come from one or the other. The authors of the registered file are the citation's, found when the call is made - by the identifier the citation gives one, which is registered and comes before any that register_authors! was given, else as register_authors! describes - and not the user. Of a source:

  • primary must be given: true if the file is the cited item or one of its files, so that the same bytes can be fetched again; false if it was requested or derived from it, as an extract is.
  • title is the file's own, where the citation's is that of a whole deposit: the files of one deposit are told apart by their titles.
  • description says more of it; for an extract, the request that made it.
  • original_store is the URL that the file was fetched from. It is recorded when it is one that other people can reach, and not for a file on this machine.
  • licence, which may be written license, is the licence's identifier in the SPDX licence list, https://spdx.org/licenses/, as CC-BY-4.0; or the URL of a licence that is not in the list. An identifier is looked for in the copy of the list that the package keeps.
  • release_date and release_version are the source's own, in place of what the citation says or lacks: a Date, a DateTime or text in ISO form as far as it goes; and a version, which is written in full, 2.1 as 2.1.0, and is 1.0.0 when there is none.

A source is one file: its identifier, title and release version may be held by any number of data products, all of the same bytes, and another file under the same three is an error, raised by this call when it has a path and otherwise by finalise before it registers anything. Such a file needs a title of its own, or the release_version it was taken from.

data_product may also be a name that a wildcard write: entry stands for - one whose name holds *s, each matching one segment - in which case that entry's file type, description and use: block are used and the name is registered as given. A name matching the patterns of several entries is an error, since nothing distinguishes them: the file type comes from the entry found, not from the caller.

supersede = true says that this version supersedes the one before it for everything made from that: once the new version is registered at finalise, an issue reading Superseded by namespace:name@vX.Y.Z is raised on the highest version before it, at severity 0, the lowest, so that identify of anything made from the old version reports it. Where there is nothing to supersede - the file is registered already, unchanged, the name has no version before, or the version written is not above the highest - nothing is raised, and an info message says so.

See also: canwrite

Several versions of one data product

A script names what it reads and writes by the labels of the working config's entries, so two versions of one data product are read, or written, under a label each, the use: block of each saying which data product and version it stands for:

read:
- data_product: temperature/older
  use:
    data_product: ECMWF/era5/t2m
    version: 1.0.0
- data_product: temperature/newer
  use:
    data_product: ECMWF/era5/t2m
    version: 2.0.0
older = link_read!(handle, "temperature/older")
newer = link_read!(handle, "temperature/newer")

A write: entry may name a version that exists, to reproduce it: the file written must then be that version's - its bytes, with the same source, authors and licence - and nothing is registered for it. Any other file is an error at finalise, before anything is registered.

Data that comes from elsewhere

A file fetched from a deposit - a dataset with a DOI, say - is registered with its source: what it is, who made it, on what terms, and where it was fetched from. A fetch run registers the files it fetches as its outputs, each with its source, and a model run reads them as it reads any other input, so that anything the model writes traces back through the fetch run to the deposit.

using DataPipeline
handle = DataPipeline.initialise()
register_authors!(handle, "authors.toml")  # ORCIDs and ROR ids of authors cited by name
era5 = "10.24381/cds.f17050d7"
# The deposit, a data product with no file, which this run reads
link_register!(handle, "deposits/era5-monthly", doi = era5, primary = true,
               licence = "CC-BY-4.0")
# An extract requested from it, which this run writes
link_write!(handle, "era5/t2m/2020", path = "cache/era5_t2m_2020.nc",
            doi = era5, primary = false, title = "ERA5 2m temperature, 2020",
            description = "the request that made it", licence = "CC-BY-4.0",
            release_version = "1.0.0")
DataPipeline.finalise(handle)

with a write: entry in the working config that covers the file - data_product: era5/t2m/*, with a file_type of nc - and nothing for the deposit, which link_register! registers itself. A DOI's own metadata gives what it has of the title, description, licence, release date and version, and the identifiers of its authors; the keywords fill in what it lacks, and take the place of what it says. A citation given as BibTeX by register_citations! is named by bibtex = instead, and serves a run with no network. Run again, a fetch run registers nothing new for a file that has not changed.

A fetch run can ask before it fetches. DataPipeline.isregistered(handle, name) says whether anything is registered under a name, and given the source keywords the link call would be given, but no file, whether registering the file would register nothing new - the same source, authors and licence. In a rehearsal in a block (see Rehearsing a run), a fetch run with nothing to fetch can then stop before a code run is registered:

using DataPipeline
nothing_to_fetch = DataPipeline.rehearse() do handle
    extract = DataPipeline.ConfigDataProduct("era5/t2m/2020")
    return DataPipeline.isregistered(handle, extract,
                                     doi = "10.24381/cds.f17050d7",
                                     primary = false,
                                     title = "ERA5 2m temperature, 2020",
                                     licence = "CC-BY-4.0",
                                     release_version = "1.0.0")
end
nothing_to_fetch && exit()
handle = DataPipeline.initialise()

A name is spelled as link_register! spells it, its namespace by default the run's default input namespace. A file that link_write! writes is asked about, as here, by the label link_write! is given, as a DataPipeline.ConfigDataProduct: the working config's write: entry says what it is registered as, and in which namespace.

A deposit may instead be registered by fair pull from a register: entry with no_file: true, or by link_register! in an earlier run. Either way a later run is offered it by a read: entry, and link_read! records it as an input and returns nothing, since it has no file.

Registering a source needs data-registry v1.4.0 or later.

DataPipeline.register_citations! — Function
register_citations!(handle, citations...)

Read citations of the sources that files come from, and keep them in the handle for the rest of the code run, each under its own key. Return the keys of the entries read, in order.

Each of citations is BibTeX text if it starts with @, and otherwise the path of a BibTeX file; either may hold several entries. An entry of any type is accepted, @dataset among them. A value written as an abbreviation must be defined in the same text, by @string with its value in quotes; a month may be a number, a name or an abbreviation of one. An entry may be read more than once, but two different entries with one key are an error, and so is a citation from which no entry can be read; a call that fails keeps nothing. Nothing is sent to the registry.

From an entry are taken its doi, as a URL in lower case, or else its url, to identify the source; its title; its authors, a person as given names then family name and an organisation as it is written; its date, or its year, month and day as far as they go, as the source's release date; its version; its note, as a description; and its license or copyright, as its licence, when that is an identifier in the SPDX licence list or a URL - any other is warned of and passed over. Braces are dropped, and LaTeX commands are left as they are.

DataPipeline.register_authors! — Function
register_authors!(handle, authors...)

Register authors with the registry together with the identifiers that say who they are - an ORCID for a person, a ROR id for an organisation - and return their names, sorted. A citation in BibTeX gives its authors by name alone: a name registered here stands, for the rest of the run, for the author with its identifier, and any other name is an author by the name alone, whatever the registry holds under it. Where a DOI's metadata identifies one of its authors, that identifier is the one for that author.

Each of authors is a name => identifier pair, or the path of a TOML file with a line for each author:

"Josiah Carberry" = "https://orcid.org/0000-0002-1825-0097"
"An Example Institute" = "https://ror.org/000000000"

A name is written as a citation's author is read: a person's given names and then family name, an organisation as it stands. An identifier is a URL, and one written with http: is registered with https:. If any of authors cannot be read, nothing is registered.

An identifier may be given several names, the spellings that citations use. The registry keeps one name for it: the one it holds already, or else the first given here, taking the arguments in order and a file's authors in order of name. A message says when another name stands for that author.

Several authors may share a name, each with an identifier of its own. A citation of a name that the run has registered with several identifiers cannot say which of them is meant: its author is recorded by the name alone, and a warning says so.

Call this before a source that names these authors is cited: an author recorded by name alone is not given an identifier afterwards.

DataPipeline.link_register! — Function
link_register!(handle, data_product; path = nothing, supersede = false,
               doi = nothing, bibtex = nothing, title = nothing,
               primary = nothing, description = nothing,
               original_store = nothing, licence = nothing,
               license = nothing, release_date = nothing,
               release_version = nothing)

Register something that comes from outside the pipeline, with its source, as the data product data_product, which the working config does not name, and record it as an input of the code run. No run made it: it is this run's input and no run's output. The data product is named as the pipeline names one, namespace:name@version, and may leave out the namespace, the version or both: name, name@1.2.3, namespace:name.

With no path it is a data product with no file - the deposit that a source's files belong to, which a run that fetches them reads, so that each file it registers as an output is derived from it - and nothing is returned. With a path it is that file, put in the data store as link_write! puts one, as a hard link where one can be made and else a copy, and its path there is returned.

The namespace is by default the run's default input namespace. The version is the data product's in the pipeline - the source's own is release_version. With none given, a name not yet registered is version 0.0.1; a name whose highest version is registered with the same file, or with none, and the same source, authors and licence is that version, and nothing new is registered; any other is the highest version's next patch. A version given that is registered already must be registered so too, or it is an error.

The source is named by doi or bibtex, and must be: title, primary, description, original_store, licence or license, release_date and release_version say of it what they say for link_write!, and primary must be given here too. original_store, where a file was fetched from, needs a path. A source is one file, as there. supersede = true is as there too: a new version registered by the call supersedes the highest before it, with an issue on that version raised at finalise, and an info message where there is nothing to supersede.

DataPipeline.isregistered — Function
isregistered(handle, data_product; doi = nothing, bibtex = nothing,
             title = nothing, primary = nothing, description = nothing,
             original_store = nothing, licence = nothing,
             license = nothing, release_date = nothing,
             release_version = nothing)

Return whether the registry holds data_product, registering and recording nothing. It is named as link_register! names one, namespace:name@version: the namespace by default the run's default input namespace, and with no version the highest. Or it is a ConfigDataProduct, the label a script gives link_write! or link_read!, resolved as the run resolves it: the write: entry naming it, or the one pattern covering it, under the name its use: block gives and in its namespace, else the run's default output namespace; else the read: entry naming it, or the kept entry whose pattern covers it. Its version is the entry's where that version is registered, else the highest, as link_write! compares an output at finalise. A label no entry covers, or several patterns cover, is a ConfigFileException, and a component of one an ArgumentError.

With no source keyword, whether anything is registered under the name, or at the version a name asks for. With the keywords link_register! or link_write! would be given, but no file, whether registering that file would register nothing new: whether the version asked about records the same source - its identifier, title and release version, from the citation that doi or bibtex names and from title and release_version - the same authors, and the same licence, licence or license. primary must be given, as there, and is not compared; nor are description, release_date and original_store, which the registry keeps as a first registration said them; nor are the file's bytes. An author the registry has not got is not registered, and makes the answer false, as registering would add one. A doi with no citation is looked up at doi.org as the link calls look it up.

So a script can ask before it fetches anything whether there is anything to fetch, and why: false by the name, nothing is registered; true by the name and false with the source, it is registered with other facts.

See also: canread, identify

Raising issues

An issue records a problem found in something registered, so that DataPipeline.identify of anything made from it reports it and DataPipeline.downstream of it says what to make again. In a run, raise_issue!(handle, target, description) queues it, and finalise registers it, so that an output can be named before it is written:

raise_issue!(handle, "SEIRS_model/parameters", "Rates are per day, not per week",
             severity = 4)
raise_issue!(handle, DataPipeline.CodeRepository(), "Fixed in the next commit")

Outside a run, an issue on something registered already - a data product, or commits of a code repository - is registered at once. A selection of commits stands for the code at each of them, so a problem fixed in a release is raised on everything before it in one call (see Releases of the code):

raise_issue!("PSU:SEIRS_model/parameters@v1.0.0", "Rates are per day, not per week")
raise_issue!(DataPipeline.AncestorCommits(of = "v1.2.0", including = false),
             "Bug X, fixed in v1.2.0")
DataPipeline.raise_issue! — Function
raise_issue!(handle, target, description; severity = 1,
             all_versions = false)
raise_issue!(handle, targets, description; severity = 1,
             all_versions = false)
raise_issue!(target, description; remote = nothing,
             severity = 1, all_versions = false)
raise_issue!(registry, target, description;
             severity = 1, all_versions = false)

Raise an issue with one thing, or with several at once as one registry issue. A target is an AbstractIssueTarget - WorkingConfig, SubmissionScript, CodeRepository, ConfigDataProduct or ExistingDataProduct - or a String: a data product of this run by its config name, as ConfigDataProduct names one, or a registered data product as namespace:name@version (namespace:name for its newest version), as ExistingDataProduct names one; or an AbstractCommitSelection, which stands for the CodeRepository of the commits it selects. severity is an integer, larger for worse, by default the registry's own default. Issues are queued in the handle and registered by finalise, so an output can be named before it is written.

A data product's bytes may be registered as other versions of the same data product too, which the issue would then not reach. finalise looks for them, and warns of any; with all_versions = true it raises the issue on every such version as well, as one issue over their components. There is no prompt, since a script may run where no one can answer.

Outside a run - given a registry, or none for the CLI's local registry or its remote registry named remote - the issue is registered at once, and its URL returned, which downstream takes as issue. Only a target that names what it is on without a run can be raised so: an ExistingDataProduct, or a string of its form, and commits - an AbstractCommitSelection, or a CodeRepository given one; any other is an ArgumentError. So raise_issue!(AncestorCommits(of = "v1.2", including = false), "Fixed in v1.2") raises an issue on the code that came before v1.2. Registering needs the registry's token, which RegistryEndpoint reads from the CLI's configuration. While the session is rehearsing a run, the issue is printed as what would be raised, nothing is registered, and nothing is returned.

Arguments

  • handle::DataRegistryHandle: the code run the issue is raised in.
  • registry::RegistryEndpoint: the registry to raise it in, outside a run.
  • target, targets: what the issue is on, as above.
  • description::String: the issue.
  • severity::Integer: larger for worse.
  • all_versions::Bool: whether to raise it on the other versions of a data product holding the same bytes too.
  • remote: with no registry given, the remote registry of that name in the current project's CLI configuration, else the CLI's local registry.
