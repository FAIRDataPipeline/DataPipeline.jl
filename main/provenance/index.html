Tracing provenance

What the pipeline records of every run - the code at its commit, what it read and what it wrote - is there to be asked. This page is what the package asks of it: what the registry knows about a file, whether the data stores hold what it records, where a file came from, what was made from it, how one version supersedes another, and the crate that packs the files of a paper with the provenance of each. None of it needs a token, so it all works outside fair run, against the local registry or a remote one.

Holding the local registry

Outside a run, each of these functions holds the local registry up through a session of the FAIR CLI's while it works: a session starts the registry where nothing holds it, and the last to close stops one a session started. Calls in a DataPipeline.registry_session block share its session, given its endpoint first; fair registry start keeps the registry running until fair registry stop.

DataPipeline.registry_session() do registry
    DataPipeline.identify(registry, "results.csv")
    DataPipeline.provenance(registry, "results.csv")
end
DataPipeline.registry_session — Function
registry_session(f; remote = nothing)

Call f with the RegistryEndpoint of the local registry, held up for as long as f runs through a session of the FAIR CLI's, which this process owns and closes when f returns or throws, and return what f returns. The endpoint is the registry the session names, with the token in the file it names. A session starts the registry where nothing holds it, and the last to close stops one a session started; a registry started by fair registry start runs until fair registry stop.

Each function that reads or writes a registry outside a run - identify, provenance, downstream, crate, register_release!, raise_issue! outside a run - holds a session for the call when given no endpoint, and takes this endpoint first to share one:

DataPipeline.registry_session() do registry
    DataPipeline.identify(registry, "figures/summary.pdf")
    DataPipeline.provenance(registry, "figures/summary.pdf")
end

With remote, the name of a remote in the project's CLI configuration, f is given that remote's endpoint instead, holding nothing. Under fair run, whose own session holds the registry, nothing is opened, and f is given the endpoint the CLI's configuration names.

Asking what the registry knows about a file or a repository

DataPipeline.identify takes a file, or commits of a git repository, and asks the registry the FAIR CLI is configured to use, or any other, what it knows about them. A selection of commits holds its repository: the top-level folder of a clone, or the URL of its remote, by default the repository holding the current directory. No token is needed, so it works outside fair run:

DataPipeline.identify("results.csv")                        # the local registry
DataPipeline.identify("results.csv", remote = "origin")     # a remote of this project
DataPipeline.identify("results.csv", superseded = true)     # and the inputs behind it since superseded
DataPipeline.identify(DataPipeline.AncestorCommits())       # this checkout's commit and its ancestors
DataPipeline.identify(DataPipeline.NamedCommit("v0.55.0"))  # one commit, by tag, branch, hash or release
# every run of this repository, including those made with uncommitted changes
DataPipeline.identify(DataPipeline.AllCommits(dirty = true))
# a repository with no clone, by the registry's record of it alone
DataPipeline.identify(DataPipeline.AllCommits(repo = "https://github.com/FAIRDataPipeline/DataPipeline.jl"))

A file's identification carries the source of a file registered from elsewhere, with the address it was fetched from; the issues raised on it and, behind it, the issues raised on anything a run on the way read, or on a run's own code, config or script, each with the run it reaches the file through; with superseded = true it lists the inputs behind the file that a newer version of has been registered since, as outdated rather than wrong.

DataPipeline.identify — Function
identify(path; remote = nothing, superseded = false)
identify(registry, path; superseded = false)
identify(handle, path; superseded = false)
identify(commits; remote = nothing)
identify(registry, commits)
identify(handle, commits)

Ask a registry what it knows about a file on disk, or about commits of a git repository.

For a file, return a FileIdentification: the data products it is registered as, where the registry expects to find it, whether a newer version of any of those data products exists, the source of any that came from elsewhere with where the file was fetched from, the issues raised against it, and the issues raised on anything behind it - the inputs read on the way to it, at the versions read, and the code, config and script of the runs on the way - each with the run it reaches the file through. With superseded = true, the inputs read on the way that a newer version of has been registered since are reported too, as outdated rather than wrong. isempty(result.objects) means the registry has no record of a file with these contents. The file is identified by the SHA-1 of its contents, as everything in the pipeline is, so a copy under another name is recognised and an edited file is not.

For commits, an AbstractCommitSelection - such as AncestorCommits(), the checked-out commit of the repository holding the current directory and its ancestors - return a RepositoryIdentification: the code runs made from the selected commits, with their outputs, and any issues raised against those commits. The repository is known to the registry by the URL of its git remote - the one named by git.remote in its .fair/cli-config.yaml, else origin - or by the URL the selection was given as its repo. Runs made with uncommitted changes are included only when the selection is made with dirty = true. When the checkout itself has uncommitted changes, AncestorCommits of the checked-out commit and CheckedOutCommit warn and use its commit as committed.

Arguments

  • path::String: the file to ask about.
  • commits::AbstractCommitSelection: the commits to ask about: AncestorCommits, CheckedOutCommit, AllCommits or NamedCommit, each holding its repository.
  • registry::RegistryEndpoint: the registry to ask, which needs no token, e.g. RegistryEndpoint("http://127.0.0.1:8000/api/"); a DataRegistryHandle may be given instead, and its registry is used.
  • remote: with no registry given, the registry is the CLI's local registry, or the remote registry of that name in the current project's CLI configuration; see RegistryEndpoint.
  • superseded: for a file, whether to report the inputs behind it that have been superseded.

DataPipeline.AbstractCommitSelection — Type
AbstractCommitSelection

Commits of a git repository: which commits, of which repository, and whether the runs made from them with uncommitted changes are included, which the registry records as <sha>-dirty. identify and downstream take one in place of a file, and raise_issue! takes one as a target. Checking the data store

DataPipeline.check_store checks the data stores on this machine - the folders of registered files that each project writes to - against the local registry: the registered files that are missing or whose contents have changed, the files there that the registry does not know, the storage locations that nothing uses, and the outputs a run left unfinished. It changes nothing.

DataPipeline.check_store()                  # hashing every registered file
DataPipeline.check_store(hashes = false)    # whether each is there, reading none
DataPipeline.check_store(quiet = false)     # every missing file, and the CLI's own

A store whose folder has gone is reported in one line, and missing files beyond a few are counted rather than listed. A changed file with more than one name was most likely written to through another: a file given to link_write! or link_register! as a path is hard-linked into the store where it can be.

DataPipeline.check_store — Function
check_store(; hashes = true, quiet = true)
check_store(registry; hashes = true, quiet = true)
check_store(handle; hashes = true, quiet = true)

Check the data stores on this machine against the local registry, and return a StoreCheck, shown as a report. A data store is a storage root that is a folder on this machine - a file:// root marked local, as fair and the APIs register each project's - and every one is checked. Found are the registered files that are missing, or whose contents are not those registered; the files in a store that the registry does not know; the storage locations that nothing uses; and the outputs that a run left under their temporary names, dat-..., as one that fails before finalise does. The check changes nothing: it deletes, moves, fetches and registers nothing.

A file put in a data store by link_write!, link_register! or link_read! with a path is a hard link where one could be made, so writing to the file at that path changes the registered one; the report says how many names a changed file has.

Arguments

  • registry: the registry whose data stores are checked, a RegistryEndpoint, which needs no token; a DataRegistryHandle may be given instead, and its registry is used. With neither, the CLI's local registry, held through a session of the CLI's while the check runs.
  • hashes: whether to hash each registered file, which reads every byte, to find those whose contents have changed; with false, only whether each is there is checked.
  • quiet: whether the report leaves out the CLI's own files under jobs/ - each run's coderuns.txt, the working config of a job no run registered - and summarises the missing files rather than listing each, giving a store whose folder has gone in one line. The check holds every finding either way.
source
DataPipeline.StoreCheck — Type
StoreCheck

What check_store found in the data stores on this machine, shown as a report.

Fields

  • roots: each data store checked, as (root, folder, exists, locations): its storage root, the folder that is, whether the folder exists, and how many storage locations the registry holds under it
  • missing: each registered file that is not there, as (path, location, hash): where it should be, the URL of its storage location and the SHA-1 registered
  • changed: each registered file whose contents are not those registered, as (path, location, hash, found, links): also its SHA-1 now and how many names it has, more than one where it is hard-linked; empty when the check was made with hashes = false
  • unknown: each file in a data store that the registry has no storage location for, other than those in unfinished and cli_files
  • unused: each storage location that nothing uses - no object, and no source as where it was fetched from - as (path, location, hash); its file is not checked further
  • unfinished: each output that a run left under its temporary name, dat-..., as (path, modified), its modification time in UTC; a run in progress has them too
  • cli_files: each file under a store's jobs/ folder that is not registered, which the CLI keeps there, such as a run's coderuns.txt
  • hashes: whether the registered files were hashed, so that changed was checked
  • quiet: whether the report leaves out the CLI's files and summarises the missing files rather than listing each

Where a file came from

DataPipeline.provenance traces a data product back: the run that made it, what that run read, the runs that made those, and so on to the data registered from elsewhere, each with its source. It takes a file, or a data product named namespace:name@version as the pipeline names one, and prints as a tree, newest first, each data product once:

DataPipeline.provenance("figures/summary.pdf")
DataPipeline.provenance("testing:SEIRS_model/report/julia@v0.0.1")
DataPipeline.provenance("testing:SEIRS_model/report/julia", depth = 2)   # two runs back
Provenance of testing:SEIRS_model/report/julia@v0.0.1  sha1 c896cfb9
<- run a1b118f0 on 2026-10-15 11:33 UTC, github.com/FAIRDataPipeline/DataPipeline.jl.git at 34d3bdca
   used testing:SEIRS_model/summary/julia@v0.0.1  sha1 b6ae4389
       issue, severity 3: an issue over an input and an output
   <- run 577160a1 on 2026-10-15 11:33 UTC, github.com/FAIRDataPipeline/DataPipeline.jl.git at 34d3bdca
      used PSU:SEIRS_model/parameters@v1.0.0  sha1 6294a595  superseded by v1.0.1  from https://doi.org/10.1038/s41592-020-0856-2 (supplement)
          issue, severity 2: an issue on the parameters
      used testing:SEIRS_model/results/model_output/julia@v0.0.1  sha1 e8912ec2
      <- run c30fbbdd on 2026-10-15 11:33 UTC, github.com/FAIRDataPipeline/DataPipeline.jl.git at 34d3bdca
         used PSU:SEIRS_model/parameters@v1.0.0  (above)

The value holds more than the tree prints - every data product, run and issue reached, keyed by registry URL - for a script to work over.

DataPipeline.provenance — Function
provenance(x; remote = nothing, depth = nothing)
provenance(registry, x; depth = nothing)
provenance(handle, x; depth = nothing)

Trace where a data product came from: the run that made it, what that run read, the runs that made those, and so on back to the data products that no run made, each with its source. Return a Trace{Upstream}, which prints as a tree, and holds every data product, run and issue reached, keyed by registry URL.

x names the data product: a file, whose contents identify it as identify does, every data product it is registered as being a root of the trace; or namespace:name@version, as the pipeline names one, with namespace:name meaning its newest version. The registry is the one the FAIR CLI is configured to use, or the project's remote named by remote, or registry, or the one handle was opened on; no token is needed.

depth is how many runs back along any path to go. By default the trace goes to the end of every path, and a data product that no run made is a root; with depth given, a data product at that depth that a run made is marked beyond, and the tree says so.

Every data product's line says whether a newer version of its name has been registered since, and the issues raised on it; an issue raised on several things is one issue, with each of them among its targets.

What was made from a file

DataPipeline.downstream traces the other way: the runs that read a data product, what they wrote, the runs that read those, and on to the end of every path. It answers "I have found a problem in this - what must be made again?": every data product reached that no newer version has superseded. It starts from a data product, from everything the runs of selected commits wrote, or from everything an issue is raised on, and prints as the mirror image of provenance:

DataPipeline.downstream("PSU:SEIRS_model/parameters@v1.0.0")
DataPipeline.downstream(DataPipeline.NamedCommit("v0.55.0"))  # what this release's runs made, and on
DataPipeline.downstream(issue = 12)                           # what an issue affects
DataPipeline.downstream — Function
downstream(x; remote = nothing, depth = nothing)
downstream(registry, x; depth = nothing)
downstream(handle, x; depth = nothing)
downstream(; issue, remote = nothing, depth = nothing)
downstream(registry; issue, depth = nothing)
downstream(handle; issue, depth = nothing)

Trace what was made from a data product: the runs that read it, what they wrote, the runs that read those, and so on to the end of every path. Return a Trace{Downstream}, which prints as a tree, and holds every data product, run and issue reached, keyed by registry URL. What must be made again, now that a problem is known in the start, is every data product reached that no newer version has superseded.

x names the start: a file, whose contents identify it as identify does, every data product it is registered as being a root; or namespace:name@version, as the pipeline names one, with namespace:name meaning its newest version; or an AbstractCommitSelection, such as AncestorCommits(), every data product the runs of the commits it selects wrote being a root, the commits found as identify finds them. With issue, the start is everything the issue is raised on - each data product, at the version it is on, and everything the runs made whose code repository, working config or submission script it is on - so that what the problem affects is what the trace holds. The issue is a TraceIssue or an IssueRecord from a trace or identify, its uuid, its registry URL, or the number the registry's own pages show it by. The registry is the one the FAIR CLI is configured to use, or the project's remote named by remote, or registry, or the one handle was opened on; no token is needed.

depth is how many runs forward along any path to go. By default the trace goes to the end of every path; with depth given, a data product at that depth that a run read is marked beyond, and the tree says so. Every data product's line says whether a newer version of its name has been registered since, and the issues raised on it.

Superseding a version

Data is often not wrong but out of date: a dataset is updated, and what was made from the old version is worth making again, though the old version was right in its day. supersede = true on a write says so. Once the new version is registered, an issue reading Superseded by namespace:name@vX.Y.Z is raised on the version before it, at severity 0, the lowest, so that identify of anything made from the old version reports it, and downstream of the old version is what to make again:

link_write!(handle, "era5/t2m/2021", path = "cache/era5_t2m_2021.nc", doi = era5,
            primary = false, supersede = true)

Where there is nothing to supersede - the file is registered already, unchanged, or the name has no version before - nothing is raised and an info message says so.

Releases of the code

A run records the commit of the code it ran. DataPipeline.register_release! records that a commit is a release - its version read from the commit's tag, v1.2.0 say, its authors and licence from the first of the repository's codemeta.json, .zenodo.json, CITATION.cff and project file that it has - as the registry's release record and as a data product, <organisation>:<repository>@<version>, which the traces and the crate take as they take any data product. A release then names the code before it, so that a problem fixed in it can be raised on everything it was found in. Its DOI - doi = "10.5281/zenodo...", or for a repository with a .zenodo.json the Zenodo DOI of its tag's version, found there - is the data product's source; one that Zenodo has not minted yet is attached by calling register_release! again later:

release = DataPipeline.register_release!(DataPipeline.NamedCommit("v1.2.0"))
raise_issue!(DataPipeline.AncestorCommits(of = release, including = false),
             "Bug X, fixed in v1.2.0")
DataPipeline.register_release! — Function
register_release!(commit = CheckedOutCommit(); website = nothing,
                  remote = nothing)
register_release!(registry, commit = CheckedOutCommit(); website = nothing)
register_release!(handle, commit = CheckedOutCommit(); website = nothing)

Register a commit of a code repository as a release of the code, and return the RegisteredRelease. The version is the commit's tag that reads as a semantic version - v1.2.0, 1.2.0-beta2 - written in full; a commit with none cannot be released.

Registered, each found rather than made where the registry holds it already: the repository's object at the commit, made as initialise makes one, with the authors, licence and keywords of the repository's metadata files; the registry's record that the commit is a release, named by the remote's path, as FAIRDataPipeline/DataPipeline.jl; and a data product of the release, <organisation>:<repository>@<version>, on the same object, so that a trace and a crate take the release as they take any data product. A second call on a release changes nothing.

The release's DOI, where it has one, is its data product's source: the version DOI given as doi, or, for a repository whose .zenodo.json says Zenodo archives its releases from GitHub, the DOI of the Zenodo version of its tag, looked up there. The DOI's metadata - its title, release date and description - describes the source, and is compared with the repository's metadata files: a difference in the authors, title, licence or version is warned of, an identifier one gives and the other lacks told of. A DOI given that cannot be looked up is an error; a Zenodo version not archived yet, or a lookup that cannot reach Zenodo or GitHub, is told of, and the release is registered without a source, which calling register_release! again attaches once it can.

A commit released already under another version - a beta, say, retagged as a release - has the new version's data product registered and its release record changed to the new version, where the registry allows it; where not, a warning says that the record keeps the old version.

While the session rehearses a run, what would be registered is printed, and nothing is.

Arguments

  • commit: the commit to release: CheckedOutCommit, the default, which a checkout with uncommitted changes cannot be, or a NamedCommit - a tag, a branch or a hash - whatever the checkout holds. Either holds its repository: a clone, or for a NamedCommit the URL of its remote, whose tags are then listed over the network and, on GitHub, whose metadata files are read at the commit.
  • website: the release's web page; by default, for a remote on GitHub, the page of the release of its tag.
  • doi: the DOI of the version released, bare or as a URL - not a concept DOI standing for every version.
  • registry::RegistryEndpoint: the registry to register it in, which needs its token; a DataRegistryHandle may be given instead, and its registry is used.
  • remote: with no registry given, the remote registry of that name in the current project's CLI configuration, else the CLI's local registry.

RegisteredRelease

The crate for a paper

DataPipeline.crate fetches the RO-Crate the registry builds for data products: a package of their files with the provenance of each, in which every run with its code at its commit, everything it read, and each data product with its source and its issues travel together. The paper's figures in one folder is the case in mind:

DataPipeline.crate("figures")                            # the metadata, parsed
DataPipeline.crate("figures", to = "paper.zip")          # the zip, files packed
DataPipeline.crate("paper", strict = false)              # the sources left out, and said
DataPipeline.crate — Function
crate(paths...; remote = nothing, depth = 100, level = nothing,
      pack = nothing, to = nothing, strict = true)
crate(registry, paths...; depth = 100, level = nothing, pack = nothing,
      to = nothing, strict = true)
crate(handle, paths...; depth = 100, level = nothing, pack = nothing,
      to = nothing, strict = true)

Fetch the RO-Crate the registry builds for data products: a package of their files with the provenance of each, as a crate's metadata describes it, in which every run with its code at its commit, everything it read, each data product with its source and its issues travel together.

Each of paths is a file, a folder, or a data product named namespace:name@version (namespace:name for its newest version). A file is identified by its contents, as identify identifies one, and every data product it is registered as is a root of the crate; a folder means every file under it, the paper's figures in one folder being the case in mind. Files and folders whose names begin with a dot are left out and reported. A file the registry does not know is an error; with strict = false such files are left out and reported, so that a folder may hold the paper's sources beside its figures.

depth is how many runs back the crate goes along any path, 100 by default. level and pack are the registry's: level 1 or 2, what travels with each file, and pack one of "none", "roots", "supplements" and "all", whose bytes a zip holds; left out, the registry's defaults apply.

Without to, return the crate's metadata, its ro-crate-metadata.json, parsed: a dictionary with "@context" and "@graph". With to, a path ending in .zip, save the crate there as that zip, the metadata and the files pack chooses, and return the path; a path ending in .json saves the metadata there. The registry is the one the FAIR CLI is configured to use, or the project's remote named by remote, or registry, or the one handle was opened on; no token is needed.
