Managing code runs

DataPipeline.initialise — Function
initialise(config_file = $FDP_CONFIG_DIR/config.yaml,
           submission_script = $FDP_CONFIG_DIR/script.sh;
           token = $FDP_LOCAL_TOKEN)

Read the working config that fair run wrote, register the config, the submission script and the code repository with the local registry, open a new code run, and return the DataRegistryHandle the rest of the API works on. The registry is run_metadata.local_data_registry_url (default http://127.0.0.1:8000/api/) and the API version run_metadata.api_version (default 1.0.0). token is the registry's access token, which registering needs; fair run sets FDP_LOCAL_TOKEN to it.

A code repository with uncommitted changes, which fair run --dirty records as a <commit>-dirty commit, gets a warning and an issue saying that the code that ran cannot be recovered from its commit.

source
DataPipeline.finalise — Function
finalise(handle)

Complete the code run: name every output file by its hash and register it, register the issues raised, attach the inputs and outputs to the code run, and append the code run's uuid to coderuns.txt beside the working config, where the CLI's fair add and fair push find it.

A file whose bytes are those of the highest version of its data product already registered is not registered again: no version is made, the file written is removed, and it is not an output of the code run. Where a link call named its source, the source, authors and licence registered with that version must be the same as well.

source
DataPipeline.DataRegistryHandle — Type
DataRegistryHandle

The state of one code run, created by initialise and completed by finalise. Every other function in the API takes one.

Fields

  • config: the working config, as read from config.yaml
  • config_dir: the directory the working config was read from, where coderuns.txt is appended to at finalise
  • registry: the RegistryEndpoint every request goes to
  • config_obj: registry URL of the object for the working config file
  • script_obj: registry URL of the object for the submission script
  • repo_obj: registry URL of the object for the remote code repository
  • datastore_obj_url: registry URL of the storage root for the data store
  • code_run_obj: registry URL of the code run
  • code_run_uuid: the code run's uuid, as the CLI's staging refers to it
  • inputs, outputs: metadata of what has been read and written so far, keyed by (data_product, component), with component nothing for a whole file
  • unchanged: what was written and found to be registered already, so that no version was made of it and it is no output of the code run; keyed as outputs is
  • issues: issues raised so far, registered at finalise
  • citations: the citations read by register_citations!, by key
  • doi_lookups: the citations looked up from a DOI so far, by the DOI's URL
  • authors: the identifiers that register_authors! has been given for each author's name

DataPipeline.RegistryEndpoint — Type
RegistryEndpoint(url, api_version = "1.0.0"; token = nothing)

A data registry to talk to: the base url of its REST API (with a trailing slash, e.g. "http://127.0.0.1:8000/api/"), the api_version sent in the Accept header of every request, and the access token sent with them, if there is one. Reading needs no token; registering anything does. initialise builds one from run_metadata.local_data_registry_url and run_metadata.api_version in the working config, with the token that fair run puts in FDP_LOCAL_TOKEN.

The token is never shown when the endpoint is printed.

DataPipeline.link_read! — Function
link_read!(handle, data_product; path = nothing, force = false)
link_read!(handle, pattern)

Return the path of the file behind a read: data product of the working config, recording it as an input of the code run.

The file is in the data store, named by its hash. For code that needs its input under a name or in a place of its own, path asks for the file there, and is what is then returned:

  • with nothing at path, the file is put there, any missing directories being made: as a hard link to the data store's file where one can be made, so that no bytes are copied, else as a copy;
  • a file already there with the same contents is left exactly as it is, whether it is the data store's file under a second name or a copy of it;
  • a file there with other contents is an error, and nothing is overwritten, unless force is true, when it is replaced by the registered file. A directory there is always an error.

A file that is a hard link is the data store's own, so it must not be written to. force does nothing without path.

Given a pattern instead - a name with one or more *, each matching one segment of a name, so that era5/t2m/* matches era5/t2m/1940-1949 but not era5/t2m/a/b - return the path of a temporary directory holding a symbolic link to the file of every read: data product that matches, each recorded as an input (the directory itself is not). A link is named after its data product with / replaced by _, plus the file's extension; the directory is named by the SHA-1 of the sorted list of link names and file hashes, so the same set of files gives the same name. The directory is removed when Julia exits. A pattern takes no path.

See also: canread

DataPipeline.link_write! — Function
link_write!(handle, data_product; path = nothing, doi = nothing,
            bibtex = nothing, title = nothing, primary = nothing,
            description = nothing, original_store = nothing,
            licence = nothing, license = nothing, release_date = nothing,
            release_version = nothing)

Return a path to write a write: data product of the working config to, in the data store, recording it as an output. finalise names the file by its hash and registers it, replacing ${{RUN_ID}} in the registered name with the code run's uuid.

path names a file that exists already, to be registered as the data product in place of one the caller writes. It is put in the data store - as a hard link where one can be made, so that no bytes are copied, else as a copy - and its path there is returned; the file at path is left as it was. Its extension must be the entry's file type. A hard link is the same file under a second name, so the file must not be written to afterwards.

A file whose bytes are those of the highest version of the data product already registered is not registered again: no version is made and it is not an output of the code run. Where the call names a source, the source, authors and licence registered with that version must be the same as well. With a path this is found as the call is made, and the path returned is that of the registered file; a file that is written afterwards is found so by finalise.

A file that comes from somewhere else is registered with its source. The source is named by its doi, or by bibtex, the key of a citation that register_citations! has read - one or the other. A DOI with no citation registered for it is looked up: its formal metadata, DataCite's record of it or else its CSL record, gives what it has of the title, the description, the licence, the release date and version, and the authors with their ORCIDs or ROR ids. Each keyword below takes the place of what the citation says, and the title and the release date must come from one or the other. The authors of the registered file are the citation's, found when the call is made - by the identifier the citation gives one, which is registered and comes before any that register_authors! was given, else as register_authors! describes - and not the user. Of a source:

  • primary must be given: true if the file is the cited item or one of its files, so that the same bytes can be fetched again; false if it was requested or derived from it, as an extract is.
  • title is the file's own, where the citation's is that of a whole deposit: the files of one deposit are told apart by their titles.
  • description says more of it; for an extract, the request that made it.
  • original_store is the URL that the file was fetched from. It is recorded when it is one that other people can reach, and not for a file on this machine.
  • licence, which may be written license, is the licence's identifier in the SPDX licence list, https://spdx.org/licenses/, as CC-BY-4.0; or the URL of a licence that is not in the list. An identifier is looked for in the copy of the list that the package keeps.
  • release_date and release_version are the source's own, in place of what the citation says or lacks: a Date, a DateTime or text in ISO form as far as it goes; and a version, which is written in full, 2.1 as 2.1.0, and is 1.0.0 when there is none.

A source is one file: its identifier, title and release version may be held by any number of data products, all of the same bytes, and another file under the same three is an error, raised by this call when it has a path and otherwise by finalise before it registers anything. Such a file needs a title of its own, or the release_version it was taken from.

data_product may also be a name that a wildcard write: entry stands for - one whose name holds *s, each matching one segment - in which case that entry's file type, description and use: block are used and the name is registered as given. A name matching the patterns of several entries is an error, since nothing distinguishes them: the file type comes from the entry found, not from the caller.

See also: canwrite

Several versions of one data product

A script names what it reads and writes by the labels of the working config's entries, so two versions of one data product are read, or written, under a label each, the use: block of each saying which data product and version it stands for:

read:
- data_product: temperature/older
  use:
    data_product: ECMWF/era5/t2m
    version: 1.0.0
- data_product: temperature/newer
  use:
    data_product: ECMWF/era5/t2m
    version: 2.0.0
older = link_read!(handle, "temperature/older")
newer = link_read!(handle, "temperature/newer")

Data that comes from elsewhere

A file fetched from a deposit - a dataset with a DOI, say - is registered with its source: what it is, who made it, on what terms, and where it was fetched from. A fetch run registers the files it fetches as its outputs, each with its source, and a model run reads them as it reads any other input, so that anything the model writes traces back through the fetch run to the deposit.

using DataPipeline
handle = DataPipeline.initialise()
register_authors!(handle, "authors.toml")  # ORCIDs and ROR ids of authors cited by name
era5 = "10.24381/cds.f17050d7"
# The deposit, a data product with no file, which this run reads
link_register!(handle, "deposits/era5-monthly", doi = era5, primary = true,
               licence = "CC-BY-4.0")
# An extract requested from it, which this run writes
link_write!(handle, "era5/t2m/2020", path = "cache/era5_t2m_2020.nc",
            doi = era5, primary = false, title = "ERA5 2m temperature, 2020",
            description = "the request that made it", licence = "CC-BY-4.0",
            release_version = "1.0.0")
DataPipeline.finalise(handle)

with a write: entry in the working config that covers the file - data_product: era5/t2m/*, with a file_type of nc - and nothing for the deposit, which link_register! registers itself. A DOI's own metadata gives what it has of the title, description, licence, release date and version, and the identifiers of its authors; the keywords fill in what it lacks, and take the place of what it says. A citation given as BibTeX by register_citations! is named by bibtex = instead, and serves a run with no network. Run again, a fetch run registers nothing new for a file that has not changed.

Registering a source needs data-registry v1.4.0 or later. Wildcard entries in the working config need fair-cli 0.10.0 or later, a pattern read of a family written more than once 0.10.1, and reading a data product pulled from a remote registry, or pushing or pulling a deposit with no file, 0.10.2.

DataPipeline.register_citations! — Function
register_citations!(handle, citations...)

Read citations of the sources that files come from, and keep them in the handle for the rest of the code run, each under its own key. Return the keys of the entries read, in order.

Each of citations is BibTeX text if it starts with @, and otherwise the path of a BibTeX file; either may hold several entries. An entry of any type is accepted, @dataset among them. A value written as an abbreviation must be defined in the same text, by @string with its value in quotes; a month may be a number, a name or an abbreviation of one. An entry may be read more than once, but two different entries with one key are an error, and so is a citation from which no entry can be read; a call that fails keeps nothing. Nothing is sent to the registry.

From an entry are taken its doi, as a URL in lower case, or else its url, to identify the source; its title; its authors, a person as given names then family name and an organisation as it is written; its date, or its year, month and day as far as they go, as the source's release date; its version; its note, as a description; and its license or copyright, as its licence, when that is an identifier in the SPDX licence list or a URL - any other is warned of and passed over. Braces are dropped, and LaTeX commands are left as they are.

DataPipeline.register_authors! — Function
register_authors!(handle, authors...)

Register authors with the registry together with the identifiers that say who they are - an ORCID for a person, a ROR id for an organisation - and return their names, sorted. A citation in BibTeX gives its authors by name alone: a name registered here stands, for the rest of the run, for the author with its identifier, and any other name is an author by the name alone, whatever the registry holds under it. Where a DOI's metadata identifies one of its authors, that identifier is the one for that author.

Each of authors is a name => identifier pair, or the path of a TOML file with a line for each author:

"Josiah Carberry" = "https://orcid.org/0000-0002-1825-0097"
"An Example Institute" = "https://ror.org/000000000"

A name is written as a citation's author is read: a person's given names and then family name, an organisation as it stands. An identifier is a URL, and one written with http: is registered with https:. If any of authors cannot be read, nothing is registered.

An identifier may be given several names, the spellings that citations use. The registry keeps one name for it: the one it holds already, or else the first given here, taking the arguments in order and a file's authors in order of name. A message says when another name stands for that author.

Several authors may share a name, each with an identifier of its own. A citation of a name that the run has registered with several identifiers cannot say which of them is meant: its author is recorded by the name alone, and a warning says so.

Call this before a source that names these authors is cited: an author recorded by name alone is not given an identifier afterwards.

DataPipeline.link_register! — Function
link_register!(handle, data_product; namespace, version = nothing,
               path = nothing, doi = nothing, bibtex = nothing,
               title = nothing, primary = nothing, description = nothing,
               original_store = nothing, licence = nothing,
               license = nothing, release_date = nothing,
               release_version = nothing)

Register something that comes from outside the pipeline, with its source, as the data product data_product, which the working config does not name, and record it as an input of the code run. No run made it: it is this run's input and no run's output.

With no path it is a data product with no file - the deposit that a source's files belong to, which a run that fetches them reads, so that each file it registers as an output is derived from it - and nothing is returned. With a path it is that file, put in the data store as link_write! puts one, as a hard link where one can be made and else a copy, and its path there is returned.

namespace is the data product's, by default the run's default input namespace. version is its version in the pipeline, as "1.0.0" or v"1.0.0" - the source's own is release_version. With none given, a name not yet registered is version 0.0.1; a name whose highest version is registered with the same file, or with none, and the same source, authors and licence is that version, and nothing new is registered; any other is the highest version's next patch. A version given that is registered already must be registered so too, or it is an error.

The source is named by doi or bibtex, and must be: title, primary, description, original_store, licence or license, release_date and release_version say of it what they say for link_write!, and primary must be given here too. original_store, where a file was fetched from, needs a path. A source is one file, as there.

Asking what the registry knows about a file or a repository

DataPipeline.identify takes a file or the top-level folder of a git repository, and asks the registry the FAIR CLI is configured to use, or any other, what it knows about it. No token is needed, so it works outside fair run:

DataPipeline.identify("results.csv")                     # the local registry
DataPipeline.identify("results.csv", remote = "origin")  # a remote of this project
DataPipeline.identify(".")                               # this checkout's commit and its ancestors
# every run of this repository, including those made with uncommitted changes
DataPipeline.identify(".", commits = DataPipeline.AllCommits(dirty = true))
DataPipeline.identify — Function
identify(path; remote = nothing, commits = AncestorCommits())
identify(registry, path; commits = AncestorCommits())
identify(handle, path; commits = AncestorCommits())

Ask a registry what it knows about a file or a git repository on disk.

For a file, return a FileIdentification: the data products it is registered as, where the registry expects to find it, whether a newer version of any of those data products exists, and any issues raised against it. isempty(result.objects) means the registry has no record of a file with these contents. The file is identified by the SHA-1 of its contents, as everything in the pipeline is, so a copy under another name is recognised and an edited file is not.

For the top-level folder of a git repository, return a RepositoryIdentification: the code runs made from its commits, with their outputs, and any issues raised against those commits. The repository is known to the registry by the URL of its git remote - the one named by git.remote in its .fair/cli-config.yaml, else origin - and commits chooses which of its commits to report. Runs made with uncommitted changes are included only when commits is given dirty = true. When the checkout itself has uncommitted changes, AncestorCommits and CheckedOutCommit warn and use its commit as committed.

Arguments

  • path::String: the file, or the repository's top-level folder, to ask about. Any other folder is an ArgumentError, including one inside a repository.
  • registry::RegistryEndpoint: the registry to ask, which needs no token, e.g. RegistryEndpoint("http://127.0.0.1:8000/api/"); a DataRegistryHandle may be given instead, and its registry is used.
  • remote: with path alone, the registry is the CLI's local registry, or the remote registry of that name in the current project's CLI configuration; see RegistryEndpoint.
  • commits::AbstractCommitSelection: for a repository, AncestorCommits() (the default), CheckedOutCommit() or AllCommits(), each optionally with dirty = true; for a file, an ArgumentError.

Raising issues

DataPipeline.raise_issue — Function
raise_issue(handle, target, description; severity = 1)
raise_issue(handle, targets, description; severity = 1)

Raise an issue with one thing, or with several at once as one registry issue. A target is an AbstractIssueTarget - WorkingConfig, SubmissionScript, CodeRepository, ConfigDataProduct or ExistingDataProduct - or a String, which names a data product of this run as ConfigDataProduct does. severity is an integer, larger for worse, by default the registry's own default. Issues are queued in the handle and registered by finalise, so an output can be named before it is written.
